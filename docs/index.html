The method

Three parts, one method

The Claude Code layer holds the rules and the team. Live Agent View is where they are seen and carried out — the shift starts there, work is dispatched from there, and what the work produced comes back through it. The third part stands on its own: a bug reporter for your clients, which works better the more the code declares about each page.

Rules

Every rule lives in the outermost layer where it is still true

One rule in one place is a rule. The same rule in two places is two rules, and sooner or later someone acts on the stale one. So there are four layers and one law — put a rule as far out as it stays true, and when two layers speak about the same thing, the specific one decides.

Specific beats general on its own concept.skills/brain/references/composition.md
CLAUDE.md read every turn — only what cannot wait for a skill to trigger
Layer 1 · craft-*any language, forever — SOLID, security, testing, git
Layer 2 · stack-* · ui-*one technology — how views.py is written in Django
Layer 3 · arch-seamswhere two technologies meet — a Django API feeding a React list
Layer 4 · the project's skillsone repository, one client — and they decide

Few routers, unlimited references. A skill's description sits in context in every session; its references/ files cost nothing until they are read. That one constraint shapes the whole layout.

Agents

The right grade for each unit — all at once

An orchestrator plans the work, names every unit, picks the agent whose grade fits each one and launches the independent ones together. A hard function gets a senior on a stronger model at higher effort; a lookup gets a scout on the cheapest one. Agents cannot learn — each starts fresh — so they are taught by editing the skills they preload.

Measurement & learning

It measures the work, then rewrites itself

When the work is done comes the audit: what each agent and skill cost, how often it ran, whether the job got done, and what you had to correct. Scores fall into bands; a weak skill gets sharpened, a losing one is deleted — and every correction you make is routed to the one place it belongs.

  1. 1
    WorkSessions, tickets, commits — the only thing that produces evidence.
  2. 2
    RecordA SessionEnd hook writes every session to journal/episodes.jsonl; usage is counted from the transcripts, not remembered.
  3. 3
    ScoreOutcomes are recorded per skill and agent and land in a band.
  4. 4
    ReviewOn a cadence — scores, coverage and the brain audit every 30 days; delegation and outcomes every 14.
  5. 5
    RewriteSharpen it, split it, move it to the right layer — or delete it. A rule proven wrong goes in the same change that found it.
✓ provenconsistently helps — preload it more widely
● workinghelps more than not — leave it alone
○ unprovenunder 5 recorded uses — not a bad score
▲ weakused often, rarely decisive — sharpen or move it
✕ retirenegative over enough uses — delete or rewrite

Bands from skills/ops-scoring. Retire on a recorded loss, never on silence.

⚙Scripts: extract once, reuse

Instead of writing a new parser every session, Claude calls a script that already hands back usable context — and the script improves with every case. attachments.py turns images and PDFs into model input and spreadsheets and documents into text, cached; similar.py finds how a ticket like this was answered before; map/scan.py draws how a project fits together.

✎Journal: patterns, not anecdotes

Every session is recorded without being asked. archivist writes the why from that record, and reads the journal back periodically to find what should become a skill, an agent or a script.

↻Workflows: one call away

A sequence done twice becomes a workflow — a deterministic script over model steps. authz-sweep.js and crud-scaffold.js run a whole multi-agent pass from one trigger.

The gate: no model, no key, no tokens

.github/workflows/brain.yml runs all three on every push. A change to a skill, a hook or hooks.json that does not keep the evals green has changed behaviour, whatever the diff looks like.

Tickets — the root of the method

One shift, from rescan to a rated resolution

This is how the work actually runs, every day. Prompts are prepared at the start of the shift instead of one at a time, related tickets go to Claude together, and every visual change comes back with a picture of itself.

  1. 1

    Start the shift

    python start.py opens the HUD. The work pill starts counting and the reminders start their clocks.

  2. 2

    Rescan

    Pulls every module from the helpdesk API and reconciles both ways, spots tickets that came back, and estimates the active tickets nobody has estimated yet — one Gemini call for the whole batch.

  3. 3

    Pick and triage

    Filter by module, category and status, then mark each ticket:

    working_todayignore_todayignore_indefinitelysolved_manuallynonsensedone

    Priority, order and context for the AI go next to it. Nothing leaves the machine until you sync.

  4. 4

    Analyse

    🔮 Analyse + suggest prompt

    Gemini reads the ticket, its comment thread and attachments, the requester's profile and the project's framework — and writes a suggested prompt for Claude. You read it before anything runs.

  5. 5

    Merge what belongs together

    🧩 Merge into 1 prompt

    Four tickets about the same screen become one prompt and one pass, instead of four sessions reading the same code four times.

  6. 6

    Send it to Claude

    Copy the prompt into a session you already have open, open it in a new terminal — or start one terminal per selected ticket:

    ⚡ Solve selected
  7. 7

    Claude works

    The work fans out to agents; the HUD, Flow and the tests rail show it live while you do something else — or answer a quiz.

  8. 8

    Before and after

    For a visual change, a pair of screenshots of the screen with every changed region enlarged, attached to the ticket comment. You choose what goes into the customer's report, and the picture shows whether the change landed where it was meant to.

  9. 9

    Close and sync

    The resolution Claude drafted and the comments you kept go out on sync. The customer sees them — and can rate the work.

  10. 10

    When a ticket comes back

    Returned / Follow-ups

    A reopened ticket lands in its own lane as a new round in the ticket's ledger. Only what was added since closing is worked on — not the whole ticket again.

Merge: four tickets, one pass

Estimates that correct themselves

Rescan asks Gemini once for every active ticket without an estimate, then corrects its answer by how far past estimates were off:

hours = gemini × median(actual ÷ estimated)
per module and scope · factor clamped to 0.25–3.0

An estimate someone already set is never overwritten.

Requester profiles

At close, one call to Gemini's cheap tier summarises how that person writes — style, habits, vocabulary — so the next vague ticket is read the way they meant it. One switch turns it off.

Bug reports from the page they happened on

A client sees /xyz on www.123.com misbehave and wants to tell you. It stands on its own — and it gets much better when the application's code tells it what each page is for.

What it collects

✂Screenshots — the visible area, a region you drag, or the whole page; marked up with arrows, boxes, pixelation and a caption.
⏺Video of the tab. The ticket gets up to six still frames; the recording itself stays in your Downloads.
⇄Network — the requests that failed or came back with a 4xx or 5xx.
⚠Console — errors, warnings and uncaught exceptions.
?A short interview — Gemini asks at most two questions a turn, then drafts. One report can become several tickets, one cause each.
➜Straight into the helpdesk through its API — title, description, module, category, priority; screenshots follow as comments.

Chrome 116+ · your own Gemini key and helpdesk token, kept in the extension's local storage and never synced. Gemini receives the report, the evidence, the visited addresses and the signed-in user's name and email as the page shows them.

Writing the app includes writing its context

Under this method every screen declares itself: a file docs/pages/<url_name>.md in the project says what the screen does not allow, why, and since when. A context processor renders it into every page, right after <body>:

<body data-page="orders:order_list" data-page-kind="list" data-role="clerk" data-tenant="acme">
<!-- page-context orders:order_list
kind: list | access: … | requires: orders.view | feature: -
NE DOZVOLJAVA: deleting an order — orders are kept for audit (orders-2026-03-01)
Prikaz: Orders of the current tenant, newest first.
-->
<!-- session-context
role: clerk | permissions: orders.view | tenant: acme
features ON: exports
features OFF that this page requires: -
-->

The two keywords stay exactly as written, because the extension's parser matches them literally: NE DOZVOLJAVA is “does not allow”, Prikaz is “what the screen shows”.

How a report is classified

  1. 1It asks for something the page declares it does not allow → limitation by design, with the reason and the tag quoted.
  2. 2The page requires a permission or a feature the session lacks → question: the client needs a right or a module, not a programmer.
  3. 3A new capability → change request.
  4. 4Anything else → bug.

Without context it still works — the wizard and the description still produce a ticket — but it will not call anything a limitation or a question: intent and rights are never guessed. It never refuses to send either; the label can be changed, or the draft dropped.

And it feeds the brain. Every ticket carries a trace tag. Every 14 days the brain reads the tags against how the tickets were closed: a limitation closed as fixed is a page that lied, a bug closed by design is a page that was silent, and screens with no declaration are ranked by the tickets they caused. The per-screen rules from ui-bootstrap ship inside the extension as its skills.
